# Specification — the nexus hub

**What this document is.** The statement of what `@typecrate/nexus` **is**, written as
requirements a build can be checked against. It is the normative answer to "what is
this package?" for anyone reading the code, and it is the contract the package is
measured against in §9 (_Conformance_) below.

**Where it sits relative to the other documents.** The original design brief
(`tasks/task-rust-hub-inference-broker.md`, 2026-11-02) has been retired from the tree
now that the build landed — its `§`-numbers are still what the source comments cite,
and the file remains readable in git history. [`README.md`](../../README.md) is the
build's own report card: verification status, resolved open decisions, known gaps.
Neither one was a specification — the brief was a wish list written before the code
existed, and the README describes one particular build. This file states the target,
independently of whether the current build hits it.

**Reading the requirements.** Each rule is `NEX-<n>` and is normative: _must_ means the
package is wrong if it does not hold. §9 records the current build's status per rule
with file-and-line evidence. Where this document deliberately narrows or extends the
task brief, §8 says so.

---

## 1. Position

Nexus is a **hub that streams data between suppliers and consumers**. A consumer posts
a _task_; the hub holds it until a supplier able to do it asks for work; the supplier
streams its result into the hub and the hub streams the same bytes out to the consumer
**while the supplier is still producing them**. Nothing is stored durably, nothing is
queued for later, nothing is written down as a matter of course: the hub is a live
conduit between two sockets.

The mental model is **Kafka-style eventing between two parties — but over real
WebSockets, not a broker log**:

| Kafka notion                | Nexus equivalent                                                                                   |
| --------------------------- | -------------------------------------------------------------------------------------------------- |
| topic                       | **pool** — an in-memory queue of tasks of one kind, identified by `PoolId`                         |
| producer / publisher        | **consumer** (the party that posts tasks; it also consumes the answer stream)                      |
| consumer group              | **supplier pool membership** — suppliers pull work; the hub gives each task to exactly one of them |
| pull-based consume + offset | supplier `Claim` → `Assigned` → seq-numbered `Frame`s → `Ack`                                      |
| partition log               | **absent, on purpose** — there is no log. See §6.                                                  |

The differences are the point. Kafka is a durable, ordered, replayable log with a disk
behind it; nexus is an **in-memory switch with a bounded, best-effort replay buffer** in
front of live sockets. A task that nobody can serve now is refused with a retryable
error rather than parked for hours. If the hub restarts, its state does not come back.
"Streams" here means _live byte relay_, not _retained stream_.

## 2. Vocabulary

| Term         | Meaning in this package                                                                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **hub**      | The nexus server process. The only public surface. Owns the queues, the leases, and the relay.                                                                            |
| **task**     | One unit of work a consumer posts. Called a _job_ in the code (`JobId`), with numbered _attempts_ after a requeue.                                                        |
| **consumer** | The party that posts a task and receives its result stream. Authenticates with an API key; identified as `ConsumerId` for subscription accounting.                        |
| **supplier** | The party that does the work. Called a _worker_ in the code (`WorkerId`). Authenticates with a pool token, **dials out** over a WebSocket, so it needs no public address. |
| **pool**     | One queue + one set of suppliers serving one task kind. The hub runs one actor per pool, and the actor is the only mutator of that pool's state.                          |
| **lease**    | Timed, exclusive ownership of a task by one supplier attempt. Renewed only by heartbeats.                                                                                 |
| **relay**    | Copying supplier output frames to consumer subscribers, verbatim, with per-job sequencing and bounded replay.                                                             |
| **orphan**   | A task whose consumer's connection has gone away while the task is still live (§5.4).                                                                                     |

## 3. NEX-1 — Implementation

> The hub is a server **written in Rust and compiled from Rust source into a native
> executable** by cargo. It ships as one binary.

- The runtime is Rust end to end: `crates/nexus-server` (axum + tokio) is the hub
  process; `crates/nexus-core` holds the queue/lease/relay logic and contains no I/O;
  `crates/nexus-worker-example` is the reference supplier client. `yarn build` produces
  the shippable binary (`cargo build --release -p nexus-server`).
- No JavaScript or TypeScript application logic participates in a request path. The
  JS/TS in the package is the Daytona/Modal deploy scripts, and no hub request touches
  them.
- The package builds for the **native target only**. A `wasm32-unknown-unknown` re-export
  of the core actor (`crates/nexus-wasm`, plus the `wasm-bindgen` glue a JS host would
  have loaded) shipped until 2026-11-14 and was retired: the package is `"private": true`,
  publishes nothing, and no other workspace package imports it — it ships one native
  binary onto a sandbox — so that build had no consumer and no test, and its Node glue
  needed a host tool (`wasm-bindgen-cli` at the exact `Cargo.lock` library version) that
  was never installed. It was always a portability affordance, never a deployment shape,
  and it must never have become a reason to move policy out of Rust: a JS host could
  perform I/O only. `crates/nexus-core` keeps its IO-free contract (no tokio, no threads,
  no `SystemTime`, injected clocks, `BTreeMap` for observable order) — that rule now stands
  on the determinism it buys the test suite, not on a second target.

_Note on the source wording._ The brief for this document says "a server build on rust,
compiled to rust". Read literally that is a tautology, so this specification records the
intended reading: **authored in Rust, compiled from Rust to a native Rust binary** — not
transpiled to another language, and not a JS server with a Rust addon. The wasm build that
used to sit next to this reading was listed because it existed, not because the brief asked
for it; it is now removed, and neither reading depends on it.

## 4. NEX-2 — The hub's job

> The hub is a nexus between suppliers and consumers: it accepts tasks, hands each one
> to exactly one supplier, and **streams** bytes between them like eventing — over real
> WebSockets.

- **NEX-2.1** The hub is the only component with a listening socket. Suppliers do not
  accept connections; they dial out and keep one persistent connection each.
- **NEX-2.2** One task is executed by exactly one supplier attempt at a time. Two
  suppliers streaming into one consumer stream is the failure this rule exists to
  prevent; the hub refuses frames from anyone but the current lease holder.
- **NEX-2.3** The hub treats task **content** as opaque. It validates envelope fields
  (kind, capability requirements, size, ids) and forwards the body; it does not parse,
  re-tokenize or rewrite a result stream mid-flight.
- **NEX-2.4** Delivery semantics are **at-most-once to the consumer, at-least-once
  across retries by explicit request**. A task is dispatched once; a lost supplier may
  cause a requeue only under the rules in §5.5, and the consumer is told in band when
  the answer is not trustworthy.
- **NEX-2.5** Cancellation is bidirectional and mandatory: a consumer that goes away
  stops the supplier (§5.4), and a supplier that dies is reported to the consumer
  (§5.5). GPU time and socket slots are both scarce, so "stream into the void" is a bug.

## 5. NEX-3 … NEX-7 — The two faces and the lifecycle

### 5.1 NEX-3 — The consumer's face

> A consumer opens a **WebSocket** to the hub, **posts tasks** on it, and **receives the
> result stream for those tasks on that same connection**.

- **NEX-3.1** One connection carries both directions: task in, result stream out. A
  consumer must not need a second connection to receive what the first one posted.
- **NEX-3.2** A connection may carry more than one task, and the stream for each task is
  tagged with that task's id so a consumer can multiplex.
- **NEX-3.3** Posting a task is acknowledged (accepted / refused) before any result
  bytes, and a refusal carries a status, a machine-readable code and, where the hub
  means "not now", a `Retry-After`.
- **NEX-3.4** The result stream is terminated by an explicit end-of-stream marker or an
  in-band error, never by silence.

### 5.2 NEX-4 — The supplier's face

> A supplier opens a **WebSocket** to the hub, **looks up tasks it can do**, **reads the
> task**, then **streams the result** back over that same connection.

- **NEX-4.1** A supplier declares what it can do on joining: pools, task kinds /
  capability requirements, concurrency capacity, and proof of what it actually loaded.
  The hub is not allowed to trust a self-declared model name as identity.
- **NEX-4.2** Work selection is **pull-driven**: the supplier asks for work, and the hub
  answers only with tasks that supplier may take — the **model it registered** is the
  model the task asks for, or the task asks for `auto`, which means "whichever model in
  this pool is free"; the supplier is ready, has a declared free slot, is not excluded
  by session affinity — except where NEX-4.7's precedence releases that gate for the
  owner of a live pin, and for nobody else — and the submitting tenant is still inside
  its concurrency budget.
  That gate has a second half, and it is **normative**: a **declared free slot**
  includes one the supplier has just **released**, so a `Ready` that raises a supplier's
  available slots re-checks that supplier's **parked claim authority** for the pool, and
  parked authority is honoured **without requiring another `Claim` or a new `Submit`**.
  The second half exists because the first one alone failed: a capacity-1 supplier
  reports its slots as busy for the whole job — the shipped supplier reports
  `free_slots = capacity - running` — then ends the job and asks for work again at once,
  while the hub is still reading the older, lower number. It parked that fresh authority
  and re-appended it every sweep, so a saturated pool dispatched **nothing** while an
  idle, willing supplier held the authority and the queue held the work, and every
  consumer watched keepalive pings until unrelated traffic happened to run the pass
  (§8.2).
  Routing keys on the model and on nothing else: the capability and context claims a
  supplier declares, and the KV headroom its engine reports, are advertisement the hub
  publishes but never gates a dispatch on. That division is deliberate, not a missing
  check — the payload is the consumer's, so an engine that cannot serve it says so
  itself and the hub relays that answer in band (§8.1.3) rather than refusing on the
  consumer's behalf for a requirement the supplier may in fact meet.
- **NEX-4.3** `Assigned` (or equivalent) carries the whole readable task: kind, resolved
  requirements, the payload, and the deadlines the supplier must respect.
- **NEX-4.4** The supplier streams output as ordered, per-task numbered frames, and ends
  with a terminal frame. Out-of-order and duplicate frames are detectable by the hub. The
  hub reads a terminal `Done` from the job's **current lease owner as a declaration, not a
  proposal**: even when its seq lags the accepted frames — the reference supplier reports
  an engine failure with `Done{start_seq}`, below everything it already streamed — it ends
  the job in band (with the lag logged), because refusing it left the record `streaming`
  forever and every consumer hanging on the keepalive pings. The refusal survives exactly
  where it protects something: a **requeued** job still refuses a previous attempt's late
  clean `Done`, so a zombie attempt cannot end the newer run.
- **NEX-4.5** The supplier must keep heartbeating while it owns a task, or the hub takes
  the task away.
- **NEX-4.6** A supplier that is not genuinely ready (model still loading, engine
  degraded) is not dispatched to, however idle it looks.
- **NEX-4.7** A consumer may **name the supplier it wants**, and the hub queues the task to
  it. The name is a `WorkerId` (§2) the hub itself handed out on an earlier answer — LOSS-3
  makes it hub-minted, one per connection, never declared by the supplier and never reused,
  so "the same supplier next time" means _that connection while it lives_: a reconnect mints
  a new id and the id the consumer is holding is permanently gone. While the named supplier
  is a **live** connection in the pool, **only it** may take the task — including while it is
  still `Loading` or momentarily has no free slot, because the consumer asked to wait for it.
  When it stops being live (disconnect, orphan-grace expiry, eviction) the reservation
  **lapses** and any model-eligible supplier may take the task; the lapse is acted on **at
  that transition**, not on the next unrelated message. A bad, unknown or malformed name is
  **never a refusal**: the task routes by model exactly as it would have without one.
    - This is an **affinity, not a scheduler**, and the two halves of that are normative.
      **The requested model stays the routing key in every case**: the name composes with
      NEX-4.2's model gate by `AND` and never overrides it, so a live pin on a supplier that
      does not serve the model simply waits and then terminates under the codes the hub already
      has (`TerminalReason::NoReadyWorker` while the record is `Pending`,
      `TerminalReason::QueueTimeout` once `Accepted` has opened the body) — no new reason code.
      And routing stays **pull-driven**: the hub never
      creates work for a pin, it only refuses _other_ suppliers at pick time, with the pinned
      task preferred ahead of older unpinned tasks **on the pin owner's own claim** so reserved
      work cannot starve behind FIFO traffic.
    - **Where the two hints disagree, the pin outranks the hash — for its owner alone.** A
      record can carry a session hint (NEX-4.2's rendezvous affinity) and a pin at the same
      time, and their targets can differ. The pin then releases **exactly one** supplier from
      the affinity gate: the id it names, and only while that link is `Live`. The asymmetry is
      the reason, not an exception: the hash is an optimisation computed over a pool membership
      the consumer never chose, and its target moves as unrelated suppliers arrive and leave,
      while the pin is an explicit consumer promise naming a connection this hub itself handed
      that consumer on the previous turn. Both express one wish — "put me back where I was
      warm" — so a record whose two hints point apart is a modelling artifact rather than a
      conflict of intent, and honouring the more specific signal is the only reading under
      which **both** headers can be satisfied. Composed by plain `AND` instead, the state is a
      **deadlock, not a choice**: the hash owner is refused by the pin, the pin owner by
      affinity, every peer by affinity, so no supplier can lease the task on any event, neither
      relaxation pass fires (both links stay healthy), and the task starves to
      `claim_deadline_ms` and answers `TerminalReason::QueueTimeout` instead of being served.
      Nothing else is released: the phase term, NEX-4.2's model gate and the tenant cap still
      bind the pin owner, so while the pin is live the task stays reachable by exactly one
      supplier — a pin remains a reservation, not a preference. On the event that lapses the
      pin, affinity re-asserts **in that same step** and the task goes to the session's
      rendezvous owner, not to an arbitrary peer.
        - The ranking settles the conflict **between the two hints**. It does not settle every
          nobody-may-lease state, and does not claim to: a session hint whose rendezvous target
          does not serve the requested model still leaves the task leasable by nobody — affinity
          refuses every peer and the model gate refuses the owner — and it terminates at the
          claim deadline under the codes above. That case predates the pin and this build leaves
          it as it found it.
    - The answer names the supplier this hub was **actually connected to**, on every face, and
      names it from the **first** lease rather than the current one; §7 spells both directions,
      says which moment the value is taken from and where the current lease is instead, and
      covers the WebSocket face, which has no header to put it in.

### 5.3 NEX-5 — Live relay

> While a supplier is still streaming, the hub is already streaming to the consumer.

- **NEX-5.1** No "wait for completion then deliver". Bytes cross the hub as they arrive,
  subject only to an explicit, bounded batching window that exists for syscall economy
  and must never exceed a stated latency budget.
- **NEX-5.2** The consumer's stream is the supplier's stream: verbatim, in order, without
  gaps. A detected gap is reported in band rather than papered over.
- **NEX-5.3** The hub keeps no per-task buffering that grows without bound. Replay
  buffers are bounded in frames and bytes; a consumer that cannot keep up is ended in
  band with a stated reason, not allowed to stall the pool.

### 5.4 NEX-6 — Lifetime coupling: no consumer, no task

> To prevent cross-streaming, a consumer that posts a task **keeps its connection open**
> for as long as it wants the answer. If it does not, the task is **orphaned and
> deleted**, and any supplier stream feeding it is **terminated automatically**.

- **NEX-6.1** The consumer's connection **is** the subscription. Its loss is an event the
  hub notices, not something discovered when a write finally fails.
- **NEX-6.2** On that event the hub stops feeding nobody: the task stops being queued,
  the supplier is told to stop producing, and further supplier frames for that task are
  not relayed to anyone.
- **NEX-6.3** The task is then **deleted**: no queue entry, no lease, no record, no
  retained stream, no idempotency entry that will hand the same answer to a later
  stranger. A task with no attached consumer has no reason to exist.
- **NEX-6.4** Termination is automatic — the supplier does not have to be asked politely
  by a third party, and the consumer does not have to send a goodbye.
- **NEX-6.5** Cross-streaming means: an answer arriving for a task nobody is listening
  to, or an answer arriving on a connection that does not own the task. Both are
  prevented by NEX-2.2 and this rule together.
- **NEX-6.6 (permitted exception).** A consumer may _explicitly_ declare a task detached
  — "post it now, I will pick the result up later". That is a different, opt-in contract
  from NEX-6.1 and must be stated as such on the request; it never applies to a plain
  "stream me the answer" submission.

### 5.5 Loss and recovery (supporting rules)

- **LOSS-1** A supplier that dies having produced **no** bytes may be requeued to
  another supplier, transparently, when the task is idempotent. A non-idempotent task
  fails loudly instead of silently running twice.
- **LOSS-2** A supplier that dies **after** bytes reached the consumer cannot be made
  invisible: the stream is ended in band with a retryable error.
- **LOSS-3** Identity is **connection-scoped**. The hub mints a fresh UUIDv4 for
  every supplier socket and reports it in `Welcome`; a supplier never declares an id.
  A dropped connection's id is retired permanently, so a reconnect is a _new_ supplier
  with no leases: it cannot resume the old attempt, and the hub never reuses the old id.
  (Resume-by-continuation, where the operator opted in, re-runs the task on the new
  supplier instead of continuing the old socket.)

### 5.6 NEX-7 — Nothing is kept

> The server keeps nothing on the server. Everything is in memory, and it streams
> accordingly.

- **NEX-7.1** Task payloads and result bytes are **memory-only**. Nothing is written to a
  filesystem, database or object store on the ordinary path.
- **NEX-7.2** In-memory state is bounded twice over — by count/bytes **and** by TTL — and
  every retained byte has a stated reason for still existing (replay for a live
  consumer, a lease that must be honoured, an answer a retry must not re-run).
- **NEX-7.3** Hub restart is allowed to lose everything. Clients must see a clean,
  retryable failure, not corruption; no recovery procedure may depend on state the hub
  kept.
- **NEX-7.4** The one permitted exception is **bulk artifact egress**: a result large
  enough that buffering it in RSS would be the wrong engineering choice may leave the
  socket and be handed off as a bounded stream to a store. That exception must be
  explicit, must be bounded, must not apply to task payloads, and must be reported as a
  deviation (§8.2) rather than treated as the default.

## 6. Explicit non-goals

These are _not_ part of what nexus is, and a reviewer should not mark their absence as
a defect:

1. **Durability / replay log.** No Kafka. A hub restart discards queues, tasks, replay
   buffers and leases. Nothing is re-read from disk on boot.
2. **Conversation memory.** The hub stores no chat history. Context arrives with the
   request; the hub may use a session hint only to keep a conversation on one supplier.
3. **Multi-replica scaling.** One process, in-process queues. A shared-backend trait is
   the upgrade path, not a current capability.
4. **Result caching.** Two different consumers asking the same question get two
   executions unless they share an idempotency key while one is in flight.
5. **Sampling fan-out** (`n > 1` completions per submission) and any per-task billing,
   accounting or audit trail beyond operational metrics.
6. **TLS termination.** The hub listens in the clear by default and expects to sit behind
   a terminator.
7. **Supplier scheduling sophistication.** Model match, readiness, declared capacity and
   session affinity are required; matching on capability claims or context/KV figures,
   tier preference, warm-cache-aware placement and latency-based ranking are not. NEX-4.7
   is not in that declined set: honouring a consumer-named supplier ranks nothing, it
   declines every other supplier for one connection's lifetime **because the consumer asked
   for it** — placement the consumer directs, not scheduling the hub performs.

## 7. Protocol expectations

The specification names the shape, not the spelling — but the spelling below is what the
package uses today, and a change to it is a change to this section.

**Supplier ↔ hub (WebSocket, JSON lines, one frame per line).**

| Direction      | Frames                                                                                                                                                                                                                                                                                                                        |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| supplier → hub | `Hello` (pools, capacity, requirements, attestation, version — **no id**) · `Ready` (heartbeat, free slots, engine readiness) · `Claim` ("give me up to N") · `Frame` (one seq-numbered output frame for one job) · `Done` (terminal) · `Resume` (only meaningful on the live connection that holds the lease) · `CancelAck`  |
| hub → supplier | `Welcome` (negotiated version, **hub-assigned UUIDv4 supplier id**, joined pools, heartbeat/lease parameters) · `Assigned` (the readable task: kind, requirements, payload, deadlines, `start_seq`, artifact upload slot) · `Ack` (flow control + resume floor) · `Cancel` (stop producing) · `Reject` · `ResumeNack` · `Bye` |

**Transport-level keepalive (supplier face).** The frames above are the application
protocol; the hub also owns the socket underneath them, and it is the only party that can
tell a supplier that is _busy_ from a supplier whose path is gone. The hub therefore pings
every supplier connection at a quarter of the `heartbeat_ms` it announced in `Welcome`
(clamped into 250 ms-5 s), and treats a stretch of total silence — not one `Ready`, not one
data frame, not one `Pong` — of `max(3 × probe, heartbeat + probe)` as a disconnect: a
`Warn`, a `Bye{reason:"heartbeat_timeout"}` (close code `1000`, reconnect expected) and the
same teardown a FIN would have taken (`worker_ws.rs:53-96`, `:251-304`; §8.2). A `Pong`
counts as liveness because every WebSocket runtime sends it without the engine being
involved, and a supplier that never pongs at all is judged only by the cadence it promised,
which is why the verdict can never land before one full heartbeat has gone unheard. Only the
_engine_ being quiet is a missed heartbeat, and that verdict stays §5.1's: dispatch is
paused, the link is not dropped.

**Consumer ↔ hub (WebSocket, JSON, one frame per text message).** This is the face §5.1
requires, and the spelling is what `crates/nexus-server/src/consumer_ws.rs` speaks today;
the shapes are `ConsumerFrame` (`crates/nexus-core/src/protocol.rs:586`) and
`HubConsumerFrame` (`:664`).

- **Route** `GET /v1/consumer` (`main.rs:141` → `consumer_ws::upgrade`,
  `consumer_ws.rs:117`). Credentials are the consumer's API key on the `Authorization`
  header, checked **before** the upgrade:
  a missing or unknown key is an HTTP `401` carrying
  `www-authenticate: Bearer realm="nexus"` (`consumer_ws.rs:121-131`), never a socket
  that opens and then closes for a reason only a frame could have said. The source
  comments call this **NEX-3.5**; §5.1 stops at NEX-3.4, so that id is a code label
  rather than a rule of this document — the behaviour is specified here, in this section
  that owns spelling.
- **Dialect.** JSON, one frame per WebSocket **text** message, tagged by a snake_case
  `type` field. The vocabulary is deliberately disjoint from the supplier's (NEX-2.2):
  one hub speaks both, and must never read a consumer frame as a supplier frame. A frame
  that fails to decode is answered **in band**, with the decoder's own machine code
  (`bad_json`, `bad_frame`, `frame_too_large`, `invalid_id`, `unknown_kind`, … —
  `CoreError::code`, `errors.rs:76-89`), and a **binary** message — the
  peer having misunderstood the dialect rather than one task having failed — is answered
  `error{code:"bad_frame"}` (`consumer_ws.rs:344-352`). Either way the connection stays
  up: one typo must not cost the other tasks that socket carries.
- **Identity.** The hub mints a fresh UUIDv4 for every consumer WebSocket and one for
  each subscription on it; the consumer never declares either. The socket id is what
  `GET /v1/observe` reports in `consumer_connections[].id`, and the subscription ids are
  what the actor keys `JobRecord::consumers` by. Both are retired with the connection and
  never reused; a reconnect is a new socket with new ids.
- **Consumer → hub.** `submit {kind, payload, pool?, requires?, priority?, detach?,
idempotency_key?, supplier?}` · `attach {job, from_seq?}` · `detach {job}` · `cancel {job}`.
  `detach` defaults to `false` (`protocol.rs:606-610`), which keeps NEX-6.1 in force: this
  connection **is** the subscription. `true` is NEX-6.6's opt-in, stated on the request as
  that rule requires. An absent `idempotency_key` means a fresh key per submit — a consumer
  that wants "do not run this twice" asks for it, rather than having identical payloads
  silently merged. `requires.model` may be the literal `auto` (`AUTO_MODEL`,
  `protocol.rs:43`): that task takes whichever model in the pool is free, which is the one
  spelling of "I do not care which of your GPUs answers" the hub recognises. `supplier`
  (`protocol.rs:616-627`) is NEX-4.7's pin, spelled as a frame field because this face has no
  headers: it carries the hub-minted id an earlier `accepted` gave back, it is absent when the
  consumer has no preference, and an id this hub never issued is a hint it declines by routing
  normally rather than a frame it refuses. `default` plus `skip_serializing_if` keep it
  wire-compatible in both directions — an old consumer's JSON still decodes, and a hub with no
  pin to honour emits byte-identical frames.
- **Hub → consumer.** The verdict first, always ahead of any event byte for that task
  (NEX-3.3): `accepted {job, kind, pool, detached, supplier?}` or `rejected {job, status, code,
message, retry_after_secs?}` — the same status and machine code the HTTP surface would
  have given. `supplier` (`protocol.rs:675-687`) is the NEX-4.7 answer on this plane: the
  supplier the task was connected to **when the hub already has one**, which is the id the
  consumer sends back on its next task to stay there. Absent means no supplier is connected
  yet — the grace window, or a queue wait — and the client has nothing to pin with; the same
  lease is readable from the task's own status view (`JobView::lease`, `model.rs:571`) for a
  task that answers late, which is why no second verdict exists for it. Then the task's
  stream, every frame tagged with the `job` it belongs to so one connection can carry
  several tasks (NEX-3.2): `meta {job, attempt, pool, kind,
state?, attached_ms?}` · `delta {job, seq, text}` · `event {job, seq, payload}` ·
  `log {job, seq, text}` · `artifact {job, seq, manifest}` · `finish {job, seq, finish,
usage?}` · `error {job?, code, message, retryable, through_seq?}` ·
  `gap {job, expected, got}` · `replay {job, from_seq}`. Only `error` may omit `job`,
  for a connection-level failure no single task owns. — and it is also the reply to a `detach` for a task this
  connection is not watching: `error{job, code:"not_attached", retryable:false}`
  (`consumer_ws.rs:900-923`). There is no stream on this connection to `end`, which is why the
  answer is `error` and not `end{reason:"detached"}`. That code is **not** in the decoder list
  above — `not_attached` is a hub-side verdict, not a `CoreError::code` — and it is a normal
  reply rather than a fault: asking to stop watching a task you are not watching, or asking
  twice, gets it each time. It became reachable a second way with the 2026-11-15 relay-lifetime
  pass: a `detach` for a task whose answer already ran out lands here too, because the stream
  that finished reclaimed its own entry in the session's watch map — which is what that pass was
  for, not a change to this contract. `meta`'s two extras (`state`,
  `attached_ms`) are filled by the face that opened the stream, from the job record it
  just read; a `meta` that arrives through the relay leaves them absent rather than
  guessing at them (`protocol.rs:747-767`).
- **One `end` per task.** Exactly one `end {job, reason, through_seq?}` follows every
  task this connection started, whatever happened in between (NEX-3.4). `reason` is
  `EndReason` (`protocol.rs:546-566`), spelled `finished` (a `finish` was delivered),
  `errored` (an in-band `error` was), `lagged` (this connection could not keep up,
  NEX-5.3), `detached` (this connection asked to stop watching; the task lives on under
  NEX-6.6) or `closed` (the connection is going away while the task is still live).
  `through_seq` is the highest seq delivered here, which is the cursor for a later
  `attach {from_seq}`.

**Transport-level keepalive (consumer face).** The hub owns the socket under these frames
too, and it probes it with the same mechanism on a separate ruler: `consumer_keepalive_ms`
(`limits.rs:150`, `60_000` by default at `:235`, settable through
`NEXUS_CONSUMER_KEEPALIVE_MS`) is this face's analogue of the supplier's `heartbeat_ms`,
so one face can be retuned without moving the other. The windows are the same arithmetic
(`consumer_keepalive_windows`, `consumer_ws.rs:178-191`): a ping every quarter of the
ruler, clamped into 250 ms-5 s, and a verdict at `max(3 × probe, ruler + probe)` of total
silence — at the default a **5 s probe and a 65 s verdict: thirteen unanswered pings**.
Any inbound frame at all resets the clock, control frames included, so a bare `Pong` the
peer's runtime sent without its application knowing anything keeps a consumer waiting ten
minutes on a queued task attached (`consumer_ws.rs:531-535`); a write queue that cannot
take the ping is **skipped for that tick** rather than counted against the peer, so the
verdict stays a statement about who answered and never about a moment of backpressure
(`consumer_ws.rs:510-521`). A ruler of `0` is the off sentinel — the socket then lives
exactly as long as its client says it does, which is what this face did before the probe,
and it kept a vanished consumer and everything it held for the life of the process. The
consequence of a false verdict is **not** the supplier's: this one is NEX-6.1/6.3 applied
to whatever the socket is attached to, so the hub **cancels and deletes** an attached
running job — record, answer and idempotency entry — and a client that stays silent past
the verdict window loses work already in flight and pays for the GPU a second time on its
retry (§9.2 item 5). A task the client declared `detach`ed is not in that set: it outlives
the connection, bounded by `detached_orphan_ttl_ms` (NEX-6.6).

**Consumer → hub (HTTP/SSE).** The OpenAI-compatible surface remains for clients that
cannot hold a WebSocket. An SSE response answers on the connection it was posted on —
§8.1.2's one-connection reading — and that response body **is** the subscription NEX-6.1
means, which is why the two completion routes carry no `detach` field at all:

- `POST /v1/chat/completions`, `POST /v1/completions` → an SSE response body (the stream)
- `POST /v1/jobs` → `202` + `GET /v1/jobs/{id}/events` (SSE) + `GET /v1/jobs/{id}/result`
    - `DELETE /v1/jobs/{id}`
- `GET /v1/jobs` (the jobs this hub currently holds a live relay for, filtered to the
  calling tenant) and `GET /v1/jobs/{id}` (one job's status)
- `GET /v1/models`, `GET /healthz`, `GET /metrics`
- **`GET /v1/observe`** — read-only whole-hub snapshot for the monitoring UI
  (`observe.rs`): readiness, one row per pool, per-worker liveness and load, the
  active jobs with their leases, and the live consumer sockets with the jobs each is
  attached to. **Open, like `/healthz`** — a browser dashboard has no API key, and the
  payload is aggregated state plus job metadata, never prompt text or answer bytes.
  It answers `200` whenever the hub is serving, including at zero ready workers and
  including when a pool actor fails to answer within the probe budget (that pool is
  named in `unresponsive_pools` instead of turning the document into a status code),
  so a monitor treats a transport failure as the only downtime signal. It is also the
  one route that _relies_ on CORS — the layer wraps every route (`main.rs`,
  `observe_cors`): any origin, `GET`/`HEAD`/`OPTIONS`, any request headers,
  no credentials.
- bulk: `GET /v1/payloads/{id}` (supplier fetch), `GET|PUT /v1/artifacts/{id}` (§8.2)

On `POST /v1/jobs` the NEX-6.6 contract is **required, not inferred**: the body must
carry `"detach": true`. An absent field or `"detach": false` is refused with
`400 detach_required` (`consumer.rs:907-914`). A route that answers `202` and hangs up
holds no subscription, so it can neither honour NEX-6.1's coupled contract — a coupled
task posted there would be orphaned and deleted before the client could poll it — nor
declare detachment on a silent client's behalf. Surfaces that do keep the connection
open are named in the refusal, because "then how do I stream the answer?" is the next
question a client asks.

**Supplier pinning (`x-supplier-id`).** NEX-4.7's name travels as the `x-supplier-id` request
header on `POST /v1/chat/completions`, `POST /v1/completions` and `POST /v1/jobs`, and as
`ConsumerFrame::Submit.supplier` on the socket face. It is optional on all four and it cannot
fail a request: a value that parses becomes the hint and a value that does not becomes no hint
at all (`adapters::ChatRequest::to_submission`, `adapters.rs:155`, the `supplier_hint` parameter
at `:162`, passed through verbatim at `:187`), so a malformed or unknown value costs a pin and
not a status code.

On the hub side the two consumer hints are **ranked, not merely ANDed** (NEX-4.7): a live pin
releases **its own owner** from the session-affinity gate and nobody else, so a request
carrying both headers whose targets differ is served by the supplier it named instead of
starving to the claim deadline. The phase term, NEX-4.2's model gate and the tenant cap are
not part of that release, and both routing predicates test liveness through one shared
reader — `live_pin` (`actor.rs:2339`), consulted by `affinity_allows` (`:2455`, the arm at
`:2460`) and by `supplier_pin_allows` (`:2374`) — so they cannot diverge about _when_ a pin
binds, which is the failure mode that would re-create the deadlock.

The **answer** carries it back. The HTTP faces set `x-supplier-id` on the response from the
task's lease — present on a successful SSE stream and on a non-streaming aggregate — and the
socket face answers with `HubConsumerFrame::Accepted.supplier`. Both read the lease the actor
holds when it forms the verdict, which is the `Effect::Accepted` it is already awaiting
(`actor.rs:382`, the `worker` field at `:412`), so the value names a supplier the consumer was
**actually connected to**, never one it merely asked for. **Which moment it names is the first
lease, not the current one.** The hub-side latch is first-write-wins (`JobRelay::note_supplier`,
`state.rs:295`, and `JobRelay::supplier` `:323` states that in its own doc), so after a requeue
— A leases, A dies, B leases and produces the answer — a head that flushes late still names
**A**. That is the moment the header is about: it exists so a consumer can ask again for the
connection it was already handed, and an id that quietly moved between two claims would report
a migrated conversation to a client whose own request never moved. Who holds the lease **now**
is a separate fact with a separate home: `GET /v1/jobs/{id}` returns the actor's own
`lease.worker` (`JobView::lease`, `model.rs:571`, field `Lease::worker` `:316`), and that is
what a caller reads after a takeover. The two answers can diverge in either direction, and both
legs are pinned — the latch keeps the first supplier through every later verdict
(`a_known_supplier_survives_every_later_verdict`, `state.rs:2239`) and names nobody once the
lease is gone (`a_join_of_a_finished_completion_names_no_supplier`, `runtime_e2e.rs:5447`).
Absence is a fact and not a capability claim: it means no supplier was connected when the
answer was formed, not that the hub does not implement the header. It is therefore omitted
on every refusal that lands before a lease exists (`4xx`/`5xx`), on a `POST /v1/jobs` `202`
whose own verdict leased nobody, and on a `202` that **joins** a task which has already
finished — the lease that carried the id has been released by then. A join names a supplier
exactly when a lease exists, on that route and on the completion routes, and a fresh `202`
names one exactly when the submit turn connected one; neither absence is a gap in the
header, and the queued case is answered on the same plane by `GET /v1/jobs/{id}`, which
returns that lease. The socket face cannot carry a header after the upgrade, which is
exactly why the `accepted` field exists: it is the header's analogue on the frame plane, not
a redundant second telling.

One timing consequence is part of the contract rather than an accident of it. On the streaming
path the response head is **held until the lease it will name**: a submission the hub admitted
while no supplier was connected does not get its headers at admission, because the face waits on
`JobRelay::supplier_watcher` (`state.rs:334`) — the watch the dispatcher writes as the `Assigned`
goes out (`JobRelay::note_supplier` `:295`, read back by `JobRelay::supplier` `:323`) — before
`consumer::supplier_before_body` (`consumer.rs:1581`) writes the head with the id in it. The wait
is bounded by the kind's own `claim_deadline_ms` (`limits.rs:68`, `600_000` ms by default at
`:206`, a kind's override honoured, resolved by `consumer.rs`'s `claim_window_ms` at
`:1469-1473` and read at `:1593`): the same interval that task was already going to sit queued
for, so there is no new timer and no new knob. **While it is held, no
byte of any kind reaches the client** — an SSE keepalive is a body byte, so it cannot precede the
head — and an intermediary on an aggressive idle timeout can therefore close a request that is
merely queued behind busy capacity. Status-before-bytes for refusals, `503 + Retry-After` ahead of
any body byte included, is **unchanged**, because every refusal arm returns before the wait
begins; and only the streaming path holds at all, since `stream: false` assembles its answer
before writing a head and the `POST /v1/jobs` `202` answers on its own verdict.

**A hangup inside that window does not cost the window.** The face arms a drop guard around the
wait (`SupplierHoldDetach`, `consumer.rs:1498`, armed at `:287-292` and disarmed at `:294` the
moment the head is writable), and hyper drops the handler future as soon as the connection is
gone: the guard turns that drop into the same `ActorMsg::Detach` the pump would have posted, so
the abandoned task is cancelled and its row deleted on the spot instead of keeping a queue
position — and, on a pinned request, a whole claim window of refusing every other consumer's
claim for a task nobody wants. A `select!` against the body channel could not do this: the
channel and its `ReceiverStream` are built _inside_ the function that assembles the body, after
the hold returns, so nothing polls them while the head is pending, and `Sender::closed` reports a
dropped receiver, not a dead peer. This is NEX-6.1's rule applied at an earlier moment, not a
second policy, and it is pinned by
`a_hangup_inside_the_head_hold_cancels_the_queued_task_it_never_leased` (`runtime_e2e.rs:6163`),
which reads the task's exit reason off `/metrics` and asserts `cancelled` rather than
`queue_timeout`.

A browser still has to be allowed to read the value back: the request direction needed no change,
the CORS layer having always allowed any request header (`main.rs`, `observe_cors`), so the hub
**exposes** `x-supplier-id` beside `x-nexus-job` and `x-nexus-chunks` on
`Access-Control-Expose-Headers` — tower-http writes that list on **non-preflight responses**, and
a preflight is not a response a page reads a header off, so that is the sufficient place for it
(`a_cross_origin_dashboard_can_read_observe`, `runtime_e2e.rs:3748`). What that list buys is a
reader, not a poster: the layer admits `GET`, `HEAD` and `OPTIONS` only (`main.rs:184-188`), so a
cross-origin page still cannot replay a pinned **`POST`**, and the header stays a
server-to-dashboard affordance on that plane.

Credentials are per direction and never shared: pool token for suppliers, API key for
consumers (including the pre-upgrade check on `GET /v1/consumer`), plus an attestation
allowlist for the model a supplier claims to have loaded. A credential is checked where
the hub has one to check it against: on a hub that configures **no** credential for a
direction (`allow_anonymous`, empty set), one that arrives anyway is ignored rather than
refused, because the hub has already declared nobody is authenticated and a secret it
cannot compare cannot be wrong. Listing a credential restores the denial for every other
value (`auth.rs:94-122`, `:169-199`) — so an `Authorization` header from a client that
sends one unconditionally is not by itself a reason for a `401`.

## 8. Deviations and interpretations recorded here

### 8.1 Interpretations of the brief

1. _"streams data between supplier and consumer like kafka eventing, but with real
   websockets"_ — read as a **shape** statement (topic-like queues, pull-based worker
   groups, live relay), not a durability statement, because the same brief also requires
   that nothing be stored (§6.1, NEX-7). Where the two readings conflict, **NEX-7 wins**:
   nexus is an in-memory conduit, not a log.
2. _"consumer … can post tasks, waiting to receive the stream"_ — read as one connection
   doing both (NEX-3.1), because NEX-6 makes that connection the subscription; a two-
   connection contract would make "keep your socket open" ambiguous.
3. _"supplier … look up any tasks that they can do, read the task"_ — read as
   **model-filtered pull** (NEX-4.2/4.3). What "can do" means is the model the supplier
   registered: the hub does not second-guess the supplier's engine from a capability list
   or a context floor, and a refusal the hub invents on those grounds would deny an
   execution the supplier could have answered. Whether the supplier may _browse_ a task
   before committing to it is **not** specified; a lookup that immediately leases is
   conforming, a peek-without-lease is permitted but not required.
4. _"the server can stream the result to the consumer"_ while the supplier is still
   streaming — read as NEX-5.1, with an explicit allowance for a bounded batching window
   (a per-token flush would cost 4× the syscalls for no perceptible gain).
5. **LOSS-2's "ended in band with a retryable error"** (§5.5) — read as the _end_ being
   the requirement, not the retryability. The operative clause is **"the stream is ended
   in band"**: the consumer is never left in silence over a stream the hub knows is
   broken. "A retryable error" describes the shape of that terminal (a typed `error`
   event with a code, a message and a `through_seq`), not a promise that re-sending the
   task reproduces the answer. Once bytes have reached the consumer, an automatic blind
   retry would run the task a second time and hand back a duplicated answer, which is
   exactly what NEX-2.4 refuses: delivery is **at-most-once to the consumer**, and
   at-least-once only **across retries by explicit request** — so the retry the hub owes
   here is the one the consumer asks for, by re-posting the task. Accordingly the
   in-band terminal for a mid-stream supplier death carries `retryable: false`
   (`ConsumerEvent::Error`, `actor.rs:3051-3067` — the batch still inside the flush
   window is relayed ahead of it by `pending_batch`, `:2646`;
   `TerminalReason::WorkerGonePartial` is deliberately outside
   `TerminalReason::retryable()`'s set, `model.rs:268-281`), because "retryable" on this
   surface means "the answer can be reproduced without duplicating output", and after
   partial delivery it cannot. With `max_continuations = 0` — the default, and the
   reading this document's §5.5 assumes — **every** mid-stream death takes this in-band
   path (`limits.rs:77`, `:164`); resume-by-continuation (task brief §7.4) is an operator
   opt-in that turns one specific case into a seam instead of a truncation, and it is
   not a change to LOSS-2.
6. **Idempotency is a dedupe table, not a result cache.** The task brief's §5.2 ("a
   duplicate submission must attach to the existing job … never enqueue a second
   execution") is the requirement; §6 item 4 keeps result _caching_ a non-goal, and
   NEX-7.2 requires every retained byte to have a stated reason. The hub therefore keeps
   a **bounded idempotency mirror** — key → (pool, job, expiry) on the hub
   (`state.rs:374`, documented at `:360-380`) plus the actor's own table and expiry index
   (`actor.rs:518-519`) —
   bounded by
   `max_idempotency_entries` (4 096) and `idempotency_ttl_ms` (600 s, must be > 0),
   pruned eagerly whenever the actor forgets a job (the `Effect::JobForgotten` arm of the
   dispatcher, `state.rs:1396-1412`, which calls `Hub::forget_job` `:569` and
   `forget_idempotency_for_job` `:987`), so a same-key retry **within**
   TTL is answered from the job the hub already routed rather than by re-executing it.
   That is a keyed _join_, not a §6.4 cache: the entry names one live-or-just-finished
   execution, it is deleted with that execution (NEX-6.3's "no idempotency entry that
   will hand the same answer to a later stranger"), it expires on its own, and two
   different consumers asking the same question without a shared key still get two
   executions. A key exists only where the client declared one: a submission that carries
   no `Idempotency-Key` is given a key minted unique per request
   (`store::unique_idempotency_key`, `store.rs:41-56`), so two byte-identical bodies are
   two conversations and never one answer handed to the second caller out of the first
   one's replay.
7. **NEX-4.1's "proof of what it actually loaded"** — enforced **when the hub has an
   allowlist**, and stated rather than hidden when it does not. Attestation compares a
   digest, so it needs digests: the allowlist itself is the operator's declaration of
   intent (`config.rs:140-157` — digests listed ⇒ membership enforced, list empty ⇒ no
   anchor, so a well-formed digest is admitted and a malformed one is still refused,
   `auth.rs:281-312`). Anonymity does not relax it: an anonymous hub that lists
   `NEXUS_MODEL_SHAS` still rejects an off-list supplier (`t13`), because the credential
   rule and the identity rule are different rules. A hub that gates its sockets on
   credentials **and** lists no digests is refused at startup, not booted — the one
   configuration that used to look healthy while closing every supplier socket at `Hello`
   (`attestation_rejected`) is now a startup error naming its three remedies.
   The pool floor is gone entirely: a supplier joins by pool NAME, and the `requires`
   it declares in `Hello` is the offer jobs are matched by — never a minimum the pool
   checks — so a supplier may subscribe under any model, including one other workers of
   the same pool already serve, while per-job routing is one predicate,
   `Requires::serves_model` (`protocol.rs:119-127`), called both by the admission
   pre-check (`PoolActor::can_satisfy`, `actor.rs:725`) and by the pull (`pick_job_for`,
   `:2263`): it compares the requested model with the registered model and nothing else,
   and `auto` matches every supplier in the pool. A submission's
   requirements are likewise only what its own body implies (model, body-derived
   capabilities, `max_tokens`, prompt estimate); the kind config's `requires` is no
   longer merged in, and survives as the default `requires` of a generic submission
   that declares none (`consumer.rs:1563`, `build_submission`; the default is taken at
   `:1598-1601`).

### 8.2 Deliberate extensions of the brief

- **Bulk artifact egress** (NEX-7.4). The package supports non-text results — images,
  video, TTS — of "tens of megabytes". Holding those in RSS while a supplier uploads and
  a consumer downloads at unpredictable speeds is a worse engineering choice than
  streaming them to disk with a TTL. This is the **only** on-host persistence in the
  design, it is opt-out (artifact kinds only, never task payloads), and it is recorded as
  a deviation from the literal "keeps nothing" of NEX-7 rather than folded into it
  silently. The opt-out is a switch, not a sentiment: `artifact_root = ""` is the
  operator's explicit "no scratch disk here" — startup's `io::ensure_root` (`main.rs:89`)
  creates nothing for an empty path, so the hub comes up with no directory at all — and a
  kind that would have written an artifact is refused **at admission** with
  `400 artifact_unavailable` before any body byte (`actor.rs:1091-1104`, asserted by
  `memory_only_mode_refuses_a_kind_that_writes_an_artifact_and_admits_the_rest`,
  `acceptance.rs:3306`) rather than failing on the supplier's first upload. What the
  default path does write, it writes bounded and transiently: one append-only staging
  file per attempt, `{object}.parts/a{attempt:04}/staging.bin` (`io.rs:759`), fed with
  O(chunk) memory into a running SHA-256 the hub measures rather than trusts
  (`io::stage_chunk`, `io.rs:809`), published by an atomic **rename** into the object
  path (`io.rs:918`) so a download never sees a half-written file and completion never
  copies the bytes twice; the TTL sweep's single `io::delete_artifact` removes the object
  **and** that parts directory (`io.rs:937-951`).
- **Hub-side probing of the supplier socket** (NEX-4.5). The brief obliges the _supplier_ to
  keep heartbeating and gives the hub the right to take the task away; it says nothing about
  who notices a supplier that cannot be reached at all. Nothing did, and the consequence was
  user-visible: a path that vanished without a FIN left a writable socket, a `WorkerRecord`
  with `link: live`, and a model in `/v1/models` with nobody behind it, because §5.1's
  missed-heartbeat rule pauses dispatch rather than dropping the link. The hub now pings each
  supplier socket on windows derived from the heartbeat it announced (§7). This is an added
  obligation on the **hub**, not on the supplier: a supplier written to the brief's letter -
  heartbeating on `heartbeat_ms` and nothing else - is unaffected, since its own heartbeat is
  inbound traffic and answers the probe. It is recorded as an extension rather than folded
  into NEX-4.5 because it moves _who detects_, and because the same obligation falls to
  anyone who embeds the actor directly: the actor cannot probe, and it has no socket to
  probe (§9.2's addendum).
- **Hub-side re-check of a released slot** (NEX-4.2). The brief obliges the _supplier_
  to report how many slots it has free and lets the hub gate a dispatch on that number;
  it says nothing about **when** the hub looks again, and this build read "again" as
  "when something else happens". Two facts of the wire decide what that costs, and both
  are stated rather than hidden. First, `free_slots` is **one-way**: the hub only ever
  learns that a slot is free from the supplier's **next** `Ready` — `dispatch()` never
  decrements the number it was handed and `finish_job()` never restores it — so the gate
  can only ever **under**-dispatch, and looking early cannot overreach: a stale-low
  number costs a job its latency, never a second owner. The **safe** direction is
  untouched and still pinned by
  `heartbeats_renew_the_lease_and_missing_heartbeats_pause_dispatch_only`
  (`acceptance.rs:2073`): a supplier that stops reporting stops getting work. Second,
  the dispatch pass is **event-driven** — it runs on `Submit`, `Done`, `Claim`, `Hello`,
  `CancelAck`, a lost job, and on `Ready`. Before this pass the `Ready` entry ran it on
  **one transition** only, the engine going from not-ready to ready, so the heartbeat
  that _released_ a slot ran no pass at all while the supplier's fresh claim authority
  sat in `deferred` and was re-appended on every sweep. It now runs on **every accepted
  `Ready`** that raises that supplier's available slots, and that frame is the only one
  that can carry the news: `free_slots` is written by a `Ready` (`actor.rs:2009`) or by
  orphaning (`:3142`) and by nothing else, so the `on_ready` re-check is the fix. The
  pass at the end of `on_tick`'s sweep is the **backstop**, and the measurement is what
  makes it one: with the pool parked and every supplier still reporting `free_slots = 0`,
  a bare `Tick` runs the pass and dispatches **nothing**, because `dispatchable()`
  requires `available_slots() > 0` (`model.rs:211-215`) and a tick is never the frame
  that raises the number. What the tick can act on is a **sweep-local** unblocking event
  — `on_tick` steps 3/4 terminating a job inside the same tick, which releases the tenant
  slot in `finish_job` and can lift a `tenant_over_cap` skip in `pick_job_for` — plus any
  ordering a future frame change might introduce. The two roles are pinned apart, not
  blended: `a_tick_cannot_invent_a_slot_the_supplier_never_reported`
  (`acceptance.rs:4376`) asserts that a tick alone cannot invent a slot no supplier ever
  reported, and that the `Ready` immediately after it does dispatch. Both sites ask the
  **same predicate** (`work_parked()`) whether anything is parked, and the pass stays
  order-preserving and idempotent — a pass with nothing to hand out leaves `claims`
  byte-identical. It is recorded as an extension rather than folded into NEX-4.2 because
  it adds an **occasion** the brief never named, and because
  the reconciliation is the hub's half of a contract the supplier writes blind: no actor
  can know a slot is free earlier than the frame that says so. Nothing else moved — no
  protocol field, no client dependency, no new authority and no new grant path, only the
  hub looking again. It lives in the actor (`on_ready`, `on_tick`), so any host that
  embeds the actor inherits the same rules with the same code; what such a host still
  owes is forwarding the supplier's `Ready`, the very frame this rule reads.
- **Unbounded dispatch queue** — a stated narrowing of NEX-7.2's "bounded by count/bytes
  **and** by TTL". The queue carries no depth bound: the hub refuses no work for capacity,
  so a submission beyond a tenant's budget is accepted and **awaited** rather than answered
  `429`, and `tenant_max_concurrent` (default 16, `limits.rs:45` `:196`) gates _dispatch_,
  not admission — the skip is `PoolActor::tenant_over_cap` (`actor.rs:2198`), consulted by
  `pick_job_for` (`:2263`) and asserted by
  `the_queue_has_no_admission_bound_over_budget_submissions_await` (`acceptance.rs:1760`)
  and `tenant_concurrency_cap_awaits_and_releases_on_terminal` (`:1772`). Two consequences
  are part of the design, not accidents of it: a job the cap is holding has its claim
  deadline **re-armed** on every expiry (`rearm_cap_held`, `:3122`), so an unrefused
  submission that nothing can run stays queued instead of timing out as
  `503 queue_timeout`; and `queue_full` survives only as the in-band terminal for a

**Addendum — the relay-lifetime pass (2026-11-15, this host, dev profile only).** §7's
open-early contract and NEX-6.x's consumer rules were always correct about _answering_; what
this pass found is that they said nothing about how long a **finished** task's hub-side state
lived, and on the deployed hub that turned into resident memory climbing at **0.76 MB per
minute** — about **48 kB retained per accepted task**, measured against roughly 15.6 tasks a
minute and 165 kB relayed per task, on one consumer socket that stayed open for 117 minutes
across some 596 tasks. The curve was the shape of the bug: a hub whose consumer sockets are
long-lived keeps one set of bookkeeping per **task**, not per **stream**.

What changed, in the order the reviewer's findings were taken:

1. **A streamed answer no longer depends on another task's cleanup to end**
   (`consumer.rs`'s `StreamPump`). All three streamed-HTTP pumps — the aggregate `POST /v1/jobs`
   answer, the OpenAI SSE body, and `GET /v1/jobs/{id}/events` — used to drain their private
   replay queue strictly before they looked at the live fan-out, the response body, or their own
   deadline. One interleaving breaks that: a join resolves the task's relay row, the actor serves
   the terminal and the dispatcher takes the row away, and only then does the join install its
   replay target and post its `Attach` — so the `ReplayTo` that follows is lookup-only and the
   queue is never written and never closed. `replay.recv()` then parks forever, inside a row the
   join's own `Subscriber` keeps alive, which is why the orphan sweep could not take it either.
   The pumps now poll both queues plus `tx.closed()` plus the caller's clock in one biased
   `select!`, and hold any live item taken before the backlog drained (`held`, FIFO) until the
   backlog closes, so what a live consumer sees, and in what order, is byte-identical to what the
   sequential pumps printed. A `detach`-after-end still answers `error{not_attached}`, unchanged.
2. **An attach abandoned after installing its replay target takes the target back out**
   (`JobRelay::abandon_replay_target`, called from the `/events` `503` path and the WS `attach`
   rejection). The receiver half of that queue dies with the handler while the sender stays in the
   row, `JobRelay::is_idle` reads an installed target as "somebody is waiting", and the sweep is
   built never to delete a row that is waiting — so those rows were permanent, one per abandoned
   attach, invisible to every test that existed.
3. **The bookkeeping is published** (`nexus_relay_rows`, `nexus_relay_subscribers`), sampled in
   the same locked pass that sweeps (`state::prune_orphaned_relays`) and merged per pool at
   render time. The label vocabulary stays `pool`; nothing existing moved.
4. **A consumer that attaches after its task went terminal is closed at once**
   (`JobRelay::add_slot` retires a slot registered on a finished relay, so the receiver sees the
   same end of stream it would have seen one moment earlier).
5. **A consumer socket is probed** (NEX-6 on this face, `consumer_keepalive_ms`), and the ruler
   shipped at **60 000 ms** rather than 20 000: a probe every quarter of the ruler clamped into
   250 ms-5 s, and a verdict after `max(3 × probe, ruler + probe)` of total silence, which at the
   default is a **5 s probe and a 65 s verdict** — thirteen unanswered probes. The arithmetic
   matters because the consumer verdict is **not** symmetric with the supplier's: a supplier
   verdict costs a connection, while a consumer verdict applies NEX-6.1/6.3 to whatever that
   socket is attached to and so **cancels and deletes** the task — record, answer and idempotency
   entry — making the client's retry pay for the GPU a second time. Nothing in the hub's own
   correctness needs a fast consumer reap, and the leak this probe exists for is a socket that is
   silent for **hours**. `0` turns the probe off, as it does on the supplier face.
6. **The hub-side watch bookkeeping of a WS session is bounded by its streams**, not by its
   socket (round one of this same pass): the per-task `watches` entry is posted back through the
   session's reap postbox when the pump ends, the pump's fan-out slot is retired by
   `state::Subscriber`'s `Drop` — synchronously, so an aborted pump cannot strand a queue — and
   the observe mirror leaves with the stream.
